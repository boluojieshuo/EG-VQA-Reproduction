# 受控对照实验报告：低 EG-F1 的原因分析

> 阶段：2026-10-30
> 模型：Qwen2.5-VL-3B-Instruct（**替代基线，不是论文 EG-Reasoner**），4-bit NF4，贪心解码
> 官方评估：`official_repo/evaluation/evidence_metrics.py` + 真实 BGE-M3
> 官方代码未修改；新增脚本位于 `scripts/`，实验产物位于 `experiments/ablation/`

## 0. 结论摘要

1. **旧 8 帧基线的输入有偏差**：推理脚本取的是 32 帧中的前 8 帧，只覆盖视频前 22.6%（逐视频实测）。
   审计同时确认：时间戳只以像素形式进入模型，提示词中没有逐帧时间；解析、单位、指标计算均正确
   （用官方函数复算 IoU-F1 与保存结果完全一致）。
2. **修正后，帧数才是主要因素**：在固定 92 题上，32 帧把 EG-F1(0.3,0.5) 从 0.0234（均匀 8 帧）
   提到 0.0686，配对 Wilcoxon p≈0.04；"全部预测在前 30 秒"的比例从 66.7% 降到 31.5%。
   单纯改提示词（D）没有效果（0.0280，p=0.25）。
3. **在 300 题分层集上，32 帧的 EG-F1(0.3,0.5)=0.0510（95% CI 0.036–0.068）**，
   55.4% 的预测与任何标准证据无时间重叠，59% 的输出完整。92 题子集的 0.0686 偏乐观。
4. **低分首先是定位失败，而不是语义匹配失败**：即使最佳配置，平均最佳 IoU 只有 0.081。
5. **不建议**在当前 8 GB 机器上跑全量 2,889 题（约 15.6 GPU 小时），原因见第 5 节。

> 所有数值均来自替代基线 Qwen2.5-VL-3B-Instruct（4-bit、零样本），不是论文 EG-Reasoner，也不是论文数值的复现。

## 1. 任务 1：现有实现审计

审计脚本：`scripts/audit_pipeline.py`；输出：`experiments/ablation/pipeline_audit.json`。

### 1.1 视频帧采样是否覆盖整个视频

**官方预处理是正确的**：`preprocess/video_clip.py::sample_frame_indices` 用
`np.linspace(0, total_frames-1, 32)` 均匀采样整段视频，并对每帧按 `frame_idx / fps` 绘制时间戳。

**本地推理存在截断问题**：`evaluation/evaluate.py::frame_paths_for_video` 在自然排序后取
`[:max_frames]`。当 `max_frames=8` 而目录里有 32 帧时，只会取前 8 帧——即整段视频的**前 22.6%**：

| 视频 | 时长 | 前 8 帧覆盖到 | 占全片 | 均匀 8 帧覆盖到 |
|---|---:|---:|---:|---:|
| QWowpe84rXw | 480.2 s | 108.4 s | 22.6% | 480.1 s |
| XEifm-iXMvs | 291.0 s | 65.7 s | 22.6% | 291.0 s |
| 4L_CdjYJRvQ | 348.9 s | 78.8 s | 22.6% | 348.9 s |
| （其余 7 个视频同样为 22.5–22.7%） | | | | |

因此**旧基线（8 帧，first）本身带有输入覆盖偏差**。本次新增 `--frame-selection uniform`，
从 32 帧中均匀取 N 帧，作为修正后的基线 A2。

> 注：官方 `evaluate.py` 默认 `max_frames=32`，等于预处理帧数，不会触发该截断；问题只在自定义较少帧数时出现。

### 1.2 输入模型的帧时间戳是否正确

- 时间戳来源：`format_mmss(frame_idx / fps)`，按秒取整，绘制在右上角。
- 已用像素级对照验证：同一帧带/不带叠加层，右上角有 431–509 个像素差异（`experiments/frame_check_test.json`），
  证明叠加确实发生。
- 抽帧结果两次运行字节级一致（32 帧 SHA-256 全同）。

### 1.3 时间戳是否真正进入模型可见输入

- 预处理：是（烧录在像素上）。
- 提示词：**否**。`evaluate.PROMPT_TEMPLATE` 只包含静态示例时间（00:10 / 00:15 等），
  不包含当前样本任何一帧的真实时间。模型获取时间的唯一通道是图上的像素文字。
- 本阶段因此新增 D 组：在官方提示词后追加"读取右上角时间戳并据此定位"的明确要求。

### 1.4 证据起止时间解析

- 官方 `parse_evidence` 支持 `HH:MM:SS`、`MM:SS`、纯秒；`start >= end` 判为无效。
- 旧基线 92 条：239 个预测区间，**0 个解析失败、0 个反转、0 个负起点**；
  11 个（4.6%）终点超过视频时长；3 条问题完全没有 evidence（3.3%）。
- 另有 7 条输出在 256 token 上限处被截断（其中 3 条连 evidence 都未闭合）。

### 1.5 时间单位

- 内部一律用秒（float）；模型文本使用 `MM:SS`；`parse_number` 同时支持三者。
- 未发现秒/毫秒混用。唯一精度损失是叠加时间戳按整秒取整（官方设计如此）。

### 1.6 区间是否被截断、反转或限制在视频开头

- 解析层：无反转、无截断。
- **输入层：有"限制在开头"的问题**（1.1 节的 first-N）。
- **模型行为层：预测确实集中在开头**：旧基线 55.1% 的问题全部预测起点 ≤30 s；
  预测起点中位数 12.0 s，标准答案 78.9 s。
- 定位质量：**73.6% 的预测与任何标准证据完全无时间重叠**，仅 15.9% 达到 IoU≥0.1，
  平均最佳 IoU 仅 0.056。

### 1.7 指标计算是否与官方一致

- 本地直接调用官方 `evidence_metrics.py`，未改写。
- 用官方 `evaluate_iou` 对旧基线预测重新计算，与已保存结果的四个 IoU 阈值全部一致
  （差值 < 1e-12），见 `pipeline_audit.json::iou_metric_consistency_with_official_recompute`。
- EG-F1 的语义相似度由真实 BGE-M3（`BAAI/bge-m3`，1024 维，CPU）计算。

### 1.8 分母与类别

- 旧基线 92 条问题：descriptive 22、temporal 24、causal 22、counterfactual 24。
- 官方聚合是"每题 F1 的算术平均"；无效预测计入 `|P|` 分母（本次为 0）。
- 官方口径与本地诊断口径在报告中分开标注。

### 1.9 审计结论（有证据）

1. **旧基线的 8 帧只看到视频前 22.6%**，这是一个真实的输入偏差，必须修正后比较。
2. 时间戳只以像素形式进入模型；提示词中没有逐帧时间。
3. 模型输出的解析、单位、指标计算均正确，指标可与官方逐位复算。
4. 即使如此，预测仍高度集中在开头，且 73.6% 无任何时间重叠——低分首先是**定位失败**，
   其次才是语义匹配问题。

### 3.5 解读（基于上表）

1. **帧数是主要因素，不是帧选择方式。** 在 8 帧内，把"前 8 帧"换成"全片均匀 8 帧"没有带来提升
   （A2 0.0234 vs A 0.0455，p=0.12，方向甚至相反）——原因在于模型本来就输出很早的时间，输入覆盖不是唯一瓶颈。
   但把帧数提高到 16、32 后，EG-F1 与 IoU-F1 单调上升，C 组相对 A2 的提升在配对检验中可检出（p≈0.04）。
2. **单纯改提示词无效。** D（8 帧 + 明确要求读取时间戳）与 A2 几乎相同（+0.0046，p=0.25），
   且"前 30 秒比例"反而升到 73.9%。这说明烧录在像素上的时间戳没有被这个 3B 模型可靠利用，
   或者模型即使"看到了"也不会改变其时间先验。
3. **定位失败仍是主要矛盾。** 即使是表现最好的 C 组，仍有 **53.6% 的预测与任何标准证据完全无时间重叠**，
   平均最佳 IoU 只有 0.084。EG-F1 的提升主要来自"更多预测碰巧挨上"，而不是精确对齐。
3b. **时间先验被部分纠正但未消失。** 预测证据起点中位数从 8 帧的 12.0 s 提升到 32 帧的 32.0 s
   （标准答案中位数 78.9 s），"全部预测在 30 秒内"的比例从 55.1% 降到 31.5%
   （`experiments/ablation/diagnostics/temporal_bias_C32.json`）。方向正确，但仍有明显提前。
4. **帧数增加带来格式退化。** 完整输出（同时含 think 和 answer）从 A 的 85/92 降到 B 的 72/92、
   C 的 45/92；C 组有 1 个非法时间戳。原因是证据行变多后 256 token 被用尽。
   由于 EG-F1 只看 evidence，这不会反映在 EG-F1 上，但会直接影响答案正确性（本阶段无法用官方答案指标衡量）。
   检查 C 组内部分层：完整输出 45 条约 0.0709，截断 47 条约 0.0664，几乎相同；
   因此 C 的 EG-F1 提升不是"截断样本碰巧得分高"造成的。
5. **反事实类仍然最差**：只有 C 组首次出现非零（0.028）。

### 3.6 输出截断补充验证（256 → 512 token）

在同一 92 题、同一 32 帧配置上把 `max_new_tokens` 从 256 提高到 512：

| 项目 | 256 | 512 |
|---|---:|---:|
| EG-F1 (0.3,0.5) | 0.0686 | 0.0669 |
| 标签齐全 | 35/92 | 36/92 |
| think 内提前结束 | 41 | 41 |
| 触及上限 | 7 | 6 |
| 平均耗时 | 19.46 s | 20.61 s |

逐题配对：0 好、1 差、91 不变；35 条原本完整的输出逐字节相同。
**token 上限不是主因**——41 条在 `<think>` 内结束的输出平均仅 45.9 token（中位数 33）；
另有 6 条在 evidence 内重复生成直至 256 上限。105.4 是全部 92 条的平均值，不能用于描述这 41 条。
完整数据见 `experiments/ablation/token_limit_comparison.json` 与
`truncation_analysis.json`；详见 `docs/FINAL_REPRODUCTION_REPORT.md` 第 5.4–5.5 节。

### 3.7 证据解释力的边界

- 单次贪心解码、92 题、CIs 很宽；除 C 外各组置信区间相互重叠。
- 这是 3B 零样本替代基线，不是 EG-Reasoner；结论只适用于该替代模型。
- 未做答案指标（无 judge API key），因此"答案正确但证据错"的联合分析无法进行。

本报告只陈述"四类都很低"，不宣称哪一类更好。

## 5. 任务 5：是否建议扩大至全量 2,889 题

### 5.1 建议：**暂不建议**（在本替代基线上）

理由（均有实测依据）：

1. **它测的是替代模型，不是论文模型。** 论文 EG-Reasoner 是 Qwen2.5-VL-7B + GRPO；本机结果是
   3B、4-bit、零样本。全量跑完只能给出"这个替代品在完整测试集上的精确低分"，不能支持任何关于论文的结论。
2. **绝对分数很低且已稳定。** 300 题的 EG-F1(0.3,0.5)=0.051（CI 0.036–0.068）。扩大到 2889 题预计把
   半宽从约 0.016 收紧到约 0.005，但不会改变"定位基本失败（55% 无重叠）"的判断。
3. **答案侧无法评估。** 没有 judge API key，官方 relaxed/strict accuracy 无法计算；
   且 32 帧配置下 41% 的输出在 256 token 处截断，答案本身不完整。全量运行得到的仍是"只有证据指标"的结果。
4. **成本不低。** 32 帧全量约 **15.6 GPU 小时**（2889 × 19.5 s），另需 336 个测试视频约 2.7 GB、
   约 10,752 帧约 1.05 GB；在当前 8 GB 笔记本 GPU 上需要一整夜以上，且期间无法做其他实验。

### 5.2 如果仍要全量，建议的做法

| 项目 | 值 |
|---|---|
| 配置 | 32 帧、全片均匀、官方提示词（本阶段最优） |
| 预计推理时间 | ≈15.6 h（8 帧 7.2 h / 16 帧 10.4 h） |
| 数据准备 | 336 视频 ≈2.7 GB；帧 ≈1.05 GB；预处理约 10 分钟 |
| 结果体积 | 预测与指标 JSON 各约 8 MB |
| 前置条件 | 先解决答案截断（提高 max_new_tokens 或限制证据行数）与 judge API |

### 5.3 如何诚实报告负面结果

- 明确写"替代基线、3B、4-bit、零样本"，不写成 EG-Reasoner。
- 报告 300 题的 EG-F1 与置信区间；说明帧数从 8→32 有小幅提升（配对检验仅 C 组可检出），
  但提示词改动无效、定位失败仍是主要瓶颈。
- 不宣称类型排序（92 题与 300 题结论相反）。
- 不把本阶段数值与论文表格并列比较；论文的语义模型与样本集均不同。
